# Windows 自動更新の検証結果

2026-10-22（JST）、Windows と Godot 4.7.2 の実際の配布用 EXE で確認した。更新テストは実セーブとは異なる `APPDATA` とインストールフォルダーを使用し、実ゲームの配置先や実セーブを変更していない。テスト用プロセスの強制終了は使用していない。

## 正式な配布ファイルの取得

旧版 1.3.0 の分離フィクスチャから、固定の GitHub 最新リリース API と実際の GitHub 配布 CDN を経由して、[v1.4.0 の公開配布ファイル](https://github.com/cloford/supply-line-trainer/releases/tag/v1.4.0) を取得した。

- ファイル: `SupplyLineTrainer_Windows_v1.4.0.zip`
- サイズ: `39,324,871 bytes`
- SHA-256: `c6caabb2a926d28d510e0a42464bbd14a0a1743fe89ad14ac7c1024d0ff40d9b`
- API・HTTPS 配布 URL・CDN リダイレクト・サイズ・SHA-256・ZIP 構成の検証を通過。
- 画面状態: 「v1.4.0 の準備ができました。再起動して更新できます」。取得後の適用は実行しなかった。

## 最終ゲーム本体への適用

別の分離テストで、旧版の更新フィクスチャから最終出力の 1.4.0 EXE/PCK へ更新し、実際の `main.gd` による起動確認を検証した。

- 補助プログラムの `result.json`: `state=applied`。
- 新しいゲームの `started.json`: ランダムな確認トークンが一致、`version=1.4.0`。
- 更新後 PCK の SHA-256: `72d189f09265b8ca2c10a40333689e1703984f9d734306c5a248602abe63b348`。最終出力と一致。
- 旧 EXE/PCK のバックアップを保持。別途配置したセーブ相当ファイルのハッシュが更新前後で一致。
- 更新後の実ゲームは `CloseMainWindow()` で通常終了した。

公開済みの 1.3.0 自体には更新機能がないため、ここでの旧版は同じ更新実装を組み込んだ分離専用フィクスチャである。公開済み旧版の利用者は初回だけ 1.4.0 を手動導入する。

## 失敗・復元

| ケース | 結果 |
| --- | --- |
| 新 EXE が Windows の実行形式として不正 | 起動に失敗し `rolled-back`。旧本体を復元して起動 |
| 新 EXE が確認トークンを返さず終了 | `rolled-back`。旧本体を復元して起動 |
| ZIP に `../escape.txt` を混入 | `rejected`。配置先に変更なし |
| API の SHA-256 と ZIP が不一致 | `rejected`。配置先に変更なし |
| Windows 上で大文字小文字だけ異なる EXE 名を混入 | `rejected`。配置先に変更なし |

いずれもセーブ相当ファイルのハッシュを保持した。初期テストで見つかった Windows PowerShell の文字コード・モジュール環境差、旧 EXE への上書きロックは、UTF-8 の明示、.NET の SHA-256、旧本体の同じフォルダー内での退避によって修正した。

## 再実行できる検証

`godot --headless --path . --script updater_tests.gd` は、数値のバージョン比較、正式版判定、信頼する URL、サイズ、SHA-256、ZIP のパス・許可ペイロードを検証する。さらにローカル HTTP で正常取得、壊れた SHA-256、404、壊れた JSON、更新なし、プレリリース、接続失敗、別スレッドでの検証後に準備完了となる状態遷移を確認し、`UPDATER_TEST_OK` を出力した。開発用実行で自動更新が無効であることも確認した。

新しいゲームが起動確認を返さず動き続けるケースでは、強制終了せずバックアップを保持して手動復元を案内する設計である。この長時間動作ケース自体は今回の実プロセス試験に含めていない。実セーブを伴う長期運用、管理者権限が必要な配置先、第三者のセキュリティ製品による遮断も今回の検証範囲外である。
