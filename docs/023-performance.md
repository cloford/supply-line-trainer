# 0.23 命中停止の切り分けと保存経路

2026-11-07、Windows・Godot 4.7.2で測定。修正前は公開済み0.22のPCK、修正後は0.23ソースを使用した。同じ外部スクリプト `performance_023_tests.gd` / `profile_game_023.gd` から実際の命中、再配置、進行、通知、保存を呼び、すべて専用APPDATA・`SLT_TEST_DATA=1` に隔離した。実ユーザーの保存を入力にせず、書き換えていない。

## 観測方法

`event_frame_us` は `_fire_shot()` とその直後の `_process(0.016)` の実行時間。`shot_us`、`checkpoint_us`、`commit_save_us`、`target_move_us`、音、HUD、進行通知UIは継承した計測用クラスで別々に測った。入れ子の値を含むため単純に足し合わせない。さらに次の実process frameを待ち、その待ち時間と次回 `_process` のCPU時間を記録した。

これはheadlessで自動駆動した代表一回の計測であり、人の試遊、GPUの表示フレーム時間、入力遅延、平均・p95の測定ではない。実描画の確認は別の統合検証で扱う。生データと各イベントの状態は [023-performance.json](023-performance.json) に収録した。計測用二スクリプトは製品PCKから除外する。

履歴は次の三条件を使った。

- 空の履歴。
- 合成payload履歴100件。各件に600個の時刻・位置・回転Dictionaryを追加した約3.9MBの測定相当payload。実際の測定APIが作った記録とは区別する。
- 有効な測定履歴100件。`V2Measurement` で各600発、600姿勢、600標的イベントを生成し `completed(60.0)` が有効になることを確認。HG/AR/BRを交互に用い、採用中3件と直前3件のプロフィール・timelineも設定した約40.8MBの隔離fixture。`V2Save.save_data()` による整合性確認と実保存に成功した。いずれも自動生成で、人が100回測定した結果ではない。

## 原因と変更

0.22は一体の撃破から `_maybe_progress_checkpoint()` → checkpoint → `_commit()` を呼び、保存候補の全体複製、全体検証、既存JSON読み込み、JSON生成、書き込み、temp再読検証を同期実行していた。実績の既読確定と5達成の一覧既読確定も別の全体commitを行う。履歴を重くすると停止時間が秒単位に増えた一方、再配置は約0.01msのままだった。状態遷移・time_scaleの停止ではなく、この同期保存が主因と判断した。

加えて、進行ビューはrefresh/context変更で武器行と実績行を破棄・再生成し、非表示の実績一覧も更新していた。射撃・命中音も発生のたびに波形を生成していた。

0.23では台帳の累計差分をライブmemoryへ即時反映し、解除・表示・通知既読もmemoryで確定する。通知・checkpoint・部隊の保存要求をrevisionとして集約し、同frameには一つだけdispatchする。workerが処理中なら最新revisionを待たせ、失敗時は最新memoryから再試行する。完了したsnapshotをライブdataへ代入しないので、保存中の次の撃破を巻き戻さない。15秒checkpoint、一時停止、終了、条件変更の確定保存を維持した。

workerには専有のsnapshotだけを渡す。射撃中に不変の履歴・採用記録は開始前に一度だけworker用cacheへ複製し、射撃frameではその巨大配列を複製しない。変更可能な枝だけをdeepcopyして渡し、workerはSceneTree/Node/ライブDictionaryを参照しない。cache更新・同期保存・終了はjoin後に直列化する。

有効測定100件では開始前のarchive cache作成923.446ms、射撃frameのsnapshot作成0.053ms、保存worker15,274.490msだった。JSON変換＋stringify自体は旧8,839.980ms、新7,873.427ms、単独の全同期保存は旧19,804.642ms、新16,821.688msで、重い保存処理そのものを短時間と見せてはいない。射撃中からこの処理と履歴全体複製を外したことが改善の中心である。巨大データでは開始前のcache作成や、一時停止・終了で未完了保存を待つ時間は残る。

一時ファイル、候補と書き込み後の検証、直前セーブ保全、renameによる確定、rename失敗時の復旧は既存の `V2Save` と同じ手順を使う。射撃・命中音は起動時に6波形を生成し、再生時はstreamを再利用する。武器5行・実績6行は固定構造にし、表示するときだけ値を更新する。射撃中の入力透過と、停止後の選択ボタンのmouse_filter復元も維持する。

## 回帰確認

現行の `integration_021_tests.gd` へ、保存失敗でも即時進行・再試行一度性、同frameの複数保存要求の集約、保存中の次撃破を古いsnapshotで戻さないこと、一時停止でpending保存の確定、実GUIクリックによる武器選択、初回の実撃破・中心固定・フォーカス停止、720p/1080p/1024×768の初回描画とboundsを追加した。無射撃で中断した測定の後も最初の自由練習の案内を残し、有効な全外し測定を完了済みなら案内を再挿入しない境界も確認。headlessは505 checksで成功。

`v2_persistence_tests.gd` には通常の本番保存経路で初回実撃破→演出完了→終了→別プロセスでintro_seenを維持する確認を追加した。既存の測定3種・採用・追加2種目の保存も継続する。既存の採点回帰、progression、save故障注入、measurement境界、更新系、表示系テストを使用し、旧テスト一式の複製は作成していない。

独立検証31 checksではworkerへの受け渡し後にライブscalar/settings/archive/profileを変更してもsnapshotを混同しないこと、失敗後の最新revision再試行、保存中終了で最新成果一件の確定、Enterスキップ・途中終了・測定除外、同期保存失敗の警告保持を確認した。短時間の自動終了ではGodotのAudioStreamWAV/Playbackの解放警告が出る回があり、workerのWeakRefが解放されることとは分けて記録した。
